# Spec: Project Context — Markdown-документи репо як контекст агентів
Spec ID: SPEC-2026-10-24-project-context
Status: approved
Supersedes: —
Modules: server, client, reviewer-core
Design: `specs/designs/2026-10-24-project-context/` (D1–D4, індекс у §Дизайн)

## Проблема й користувач
Користувач DevDigest (тімлід / автор агентів) хоче, щоб рев'ю-агенти знали
правила проєкту, записані в Markdown-документах репозиторію: PRD, специфікації,
security-baseline, інсайти після інцидентів. Зараз так зробити не можна: у
промпт потрапляють лише diff, опис PR, скіли, intent і repo-intel. Поле
`specs` у збірці промпту існує, але сервер завжди передає його порожнім
(`specs_read: []`). Немає сторінки, де видно документи репо, немає способу
прикріпити їх до агента чи скіла, не видно, скільки токенів це додасть, і в
трасі запуску не можна перевірити, який текст отримала модель.

## Goals / Non-goals
**Goals**
- Знайти й переглянути всі `*.md` / `*.mdx` документи клонованого репо на
  сторінці Project Context.
- Прикріплювати документи до агентів і скілів (на сторінці та у вкладках
  Context), задавати їхній порядок і бачити оцінку токенів для кожного
  документа й загальну.
- Під час запуску агента зчитувати прикріплені документи з репо (tip базової
  гілки PR) і додавати їхній повний текст у промпт як untrusted-блок
  `## Project context` із бюджетом 8 000 токенів на один LLM-виклик.
- У трасі запуску показувати список прочитаних документів і повний текст
  вставленого блоку.

**Non-goals**
- Редагування, створення, завантаження файлів і тек на сторінці Project
  Context (кнопки New, Folder, Upload і режим Edit з D1). Документи лишаються
  read-only і беруться з git.
- Кільце Coverage («78») і футер «Indexed: N files · N chunks» з D1:
  індексація / ембедінги документів (`code_chunks.source = 'spec'`) — окрема
  майбутня спека.
- Нове per-doc поле в контракті траси (`specs_detail`): REC4 відхилено.
- Рядок «Skills loaded» у Configuration шухляди запуску (D4) належить фічі
  Skills і цією спекою не реалізується.
- Сайдбар: додається лише пункт «Project Context». Решта намальованих на D1–D4
  пунктів (Onboarding Tour, Eval Dashboard, Memory, Multi-Agent Review, Agent
  Performance, CI Runs) — non-goal. Нової клавіатурної комбінації `g …` немає
  (REC7 відхилено).
- Зміни MCP-сервера: `run_agent_on_pr` отримує контекст через той самий
  маршрут рев'ю.
- Збереження snapshot документів окремо від траси: повний вставлений текст
  уже зберігається в `run_traces` (`prompt_assembly.specs`).
- Зміни синхронізації клону: fetch базової гілки під час запуску не робиться
  (AC79).

## User stories
- **US1** Як автор агентів, я бачу всі Markdown-документи активного репо й
  читаю будь-який із них у прев'ю, щоб вибрати, що дати агентам як контекст.
- **US2** Як автор агентів, я прикріплюю документи до агента у вкладці Context,
  задаю порядок і бачу кількість токенів, щоб контролювати вартість і зміст
  промпту.
- **US3** Як автор скілів, я прикріплюю документи до скіла, щоб кожен агент із
  цим скілом успадкував їх.
- **US4** Як користувач сторінки Project Context, я бачу, хто використовує
  вибраний документ, і прикріплюю його до агентів і скілів, не відкриваючи їхні
  редактори.
- **US5** Як рецензент PR, я хочу, щоб запуск агента сам зчитував прикріплені
  документи з репо й додавав їхній текст у промпт, щоб рев'ю враховувало
  правила проєкту.
- **US6** Як автор агентів, я відкриваю трасу запуску й читаю повний текст
  блоку Project context, щоб перевірити, що саме отримала модель.

- Server-тести `server/test/prompt-structured.test.ts` і

- Seed без змін: seed-репо `acme/payments-api` не клоноване
  (`clonePath: null`), тож e2e перевіряє стан «не клоновано». Наявні
  e2e-флоу не зачіпаються.

## Acceptance criteria (EARS)

### Пошук документів (API)
- **AC1** (event, US1) КОЛИ клієнт запитує `GET /repos/:id/context` для репо з клоном, API повинен (shall) повернути всі файли з розширенням `.md` або `.mdx` з робочого дерева клону, крім файлів у теках `node_modules/`, `.git/`, `dist/`, `build/`, `vendor/` та в будь-якій теці, чия назва починається з `.`, за винятком `.devdigest/`, відсортовані за `path` за зростанням. `[unit]`
- **AC2** (ubiquitous, US1) Кожен документ у відповіді `GET /repos/:id/context` повинен (shall) містити `path` (відносно кореня репо), `folder` (тека файлу з `/` в кінці або `""` для кореня), `category`, `size` (байти), `tokens` і `status` (`ok` | `too_large`). `[unit]`
- **AC3** (ubiquitous, US1) Система повинна (shall) визначати `category` так: `specs`, якщо шлях містить сегмент `specs` або ім'я файлу закінчується на `.prd.md`; інакше `insights`, якщо шлях містить сегмент `insights` або ім'я файлу `INSIGHTS.md`; інакше `docs`. `[unit]`
- **AC4** (unwanted, US1) ЯКЩО файл більший за 1 048 576 байт, ТОДІ API повинен (shall) повернути його зі `status: "too_large"` і `tokens: null`, не читаючи вміст. `[unit]`
- **AC5** (unwanted, US1) ЯКЩО в репо знайдено понад 500 документів, ТОДІ API повинен (shall) повернути перші 500 за `path` і `truncated: true`; в інших випадках `truncated: false`. `[unit]`
- **AC6** (unwanted, US1) ЯКЩО репо не має клону (`clone_path` порожній) або тека `clone_path` відсутня чи не є git-репозиторієм, ТОДІ API повинен (shall) відповісти 409 з кодом `repo_not_cloned` (а не 500). `[unit]`
- **AC7** (unwanted, US1) ЯКЩО репо з `:id` не існує у воркспейсі, ТОДІ API повинен (shall) відповісти 404 на `GET /repos/:id/context`, `/context/file` і `/context/usage`. `[unit]`
- **AC8** (event, US1) КОЛИ клієнт запитує `GET /repos/:id/context/file?path=<p>` для документа зі `status: "ok"`, API повинен (shall) повернути його `path` і повний вміст з робочого дерева клону. `[unit]`
- **AC9** (unwanted, US1) ЯКЩО `path` у запиті до `/context/file` абсолютний, містить сегмент `..`, після розв'язання symlink веде за межі клону, не має розширення `.md`/`.mdx` або лежить у виключеній теці з AC1, ТОДІ API повинен (shall) відповісти 422 (`validation_error`) і не читати файл. `[unit]`
- **AC10** (unwanted, US1) ЯКЩО коректного `path` немає в клоні або файл більший за 1 048 576 байт, ТОДІ API повинен (shall) відповісти 404 на `/context/file`. `[unit]`
- **AC11** (ubiquitous, US2) Система повинна (shall) рахувати `tokens` документа токенізатором cl100k по точному тексту, який цей документ додає в промпт (вміст в untrusted-обгортці з AC62). `[unit]`
- **AC75** (unwanted, US1) ЯКЩО під час сканування трапляється symlink на теку, ТОДІ API не повинен (shall not) заходити в неї. ЯКЩО symlink на файл після розв'язання веде за межі клону, ТОДІ API не повинен (shall not) включати його у відповідь. `[unit]`

### Сторінка Project Context (D1)
- **AC12** (ubiquitous, US1) UI повинен (shall) показувати в сайдбарі в групі WORKSPACE пункт «Project Context» (як на D1–D4) без клавіатурної комбінації. Пункт веде на `/repos/:repoId/context` активного репо, і на цьому маршруті він підсвічений як активний. `[unit]`
- **AC13** (ubiquitous, US1) Сторінка Project Context повинна (shall) показувати документи активного репо, згруповані за `folder` (заголовок групи — тека, `/` для кореня), у кожному рядку — ім'я файлу, а в шапці списку — «PROJECT CONTEXT» і кількість документів «{count, plural, one {# document} other {# documents}}». `[unit]`
- **AC14** (event, US1) КОЛИ список документів завантажено й він непорожній, UI повинен (shall) вибрати документ із query-параметра `?doc=<path>`, якщо він є в списку (з будь-яким `status`). Інакше — перший документ зі `status: "ok"`, а якщо таких немає — перший документ списку. Вибраний рядок підсвічено, а його `path` записано в `?doc=`. `[unit]`
- **AC15** (event, US1) КОЛИ користувач клацає документ зі `status: "ok"` у списку, UI повинен (shall) показати праворуч його ім'я в шапці й вміст, відрендерений як GFM-Markdown. `[unit]`
- **AC81** (unwanted, US1) ЯКЩО вибраний документ має `status: "too_large"`, ТОДІ панель прев'ю повинна (shall) показати ім'я файлу й повідомлення «This document is larger than 1 MB and can't be previewed.» без запиту вмісту. `[unit]`
- **AC16** (state, US1) ПОКИ список документів, прев'ю на сторінці або вміст шухляди прев'ю (AC48) завантажуються, UI повинен (shall) показувати скелетони на їхньому місці. `[unit]`
- **AC17** (unwanted, US1) ЯКЩО в клонованому репо немає жодного документа, ТОДІ UI повинен (shall) показати порожній стан із заголовком «No Markdown documents found» і текстом «Add .md files to the repository (for example under specs/ or docs/) and press Refresh.». `[unit]`
- **AC18** (unwanted, US1) ЯКЩО API відповідає `repo_not_cloned`, ТОДІ сторінка повинна (shall) показати порожній стан із текстом «Repository isn't cloned yet — sync it to see its documents.». `[unit]` `[e2e]`
- **AC19** (unwanted, US1) ЯКЩО у воркспейсі немає активного репо, ТОДІ сторінка повинна (shall) показати порожній стан «Add a repository to see its documents.» з посиланням на `/onboarding`. `[unit]`
- **AC20** (ubiquitous, US1) UI повинен (shall) показувати документ зі `status: "too_large"` у списку сторінки й серед неприкріплених рядків вкладок Context приглушеним рядком із позначкою «too large (> 1 MB)», без кнопки Preview і без checkbox для прикріплення. На сторінці такий рядок можна вибрати, і тоді діє AC81. `[unit]`
- **AC21** (optional, US1) ДЕ відповідь має `truncated: true`, UI повинен (shall) показувати під списком повідомлення «Showing the first 500 documents.». `[unit]`
- **AC22** (unwanted, US1) ЯКЩО завантаження списку завершилося помилкою (крім `repo_not_cloned`), ТОДІ UI повинен (shall) показати стан помилки «Couldn't load documents» з кнопкою Retry, яка повторює запит. `[unit]`
- **AC23** (unwanted, US1) ЯКЩО завантаження прев'ю завершилося помилкою, ТОДІ UI повинен (shall) показати в панелі прев'ю «Couldn't load document» з кнопкою Retry, не скидаючи вибір у списку. `[unit]`
- **AC24** (ubiquitous, US4) UI повинен (shall) показувати в шапці прев'ю «Used by {a, plural, one {# agent} other {# agents}} · {s, plural, one {# skill} other {# skills}}» для вибраного документа, де a і s — кількість агентів і скілів, які прикріпили цей `path` для активного репо. `[unit]` `[it]`
- **AC25** (event, US4) КОЛИ користувач відкриває меню «Attach to…» у шапці прев'ю документа зі `status: "ok"`, UI повинен (shall) показати два розділи, «Agents» і «Skills», зі всіма агентами й скілами воркспейсу та checkbox, позначеним для тих, хто вже прикріпив вибраний документ для активного репо. `[unit]`
- **AC26** (event, US4) КОЛИ користувач позначає агента чи скіл у меню «Attach to…», система повинна (shall) додати документ у кінець його списку прикріплень для активного репо. `[unit]` `[it]`
- **AC83** (event, US4) КОЛИ користувач знімає позначку з агента чи скіла в меню «Attach to…», система повинна (shall) прибрати документ з його списку прикріплень для активного репо, зберігши порядок решти. `[unit]` `[it]`
- **AC27** (unwanted, US4) ЯКЩО збереження з меню «Attach to…» не вдалося, ТОДІ UI повинен (shall) повернути checkbox у попередній стан і показати toast «Couldn't update attachments: {message}». `[unit]`
- **AC28** (ubiquitous, US1) Сторінка Project Context повинна (shall) мати в тулбарі списку лише кнопку Refresh і не повинна (shall) показувати New, Folder, Upload, перемикач Edit, кільце Coverage й футер «Indexed…» з D1. `[unit]`

### Вкладки Context агента (D2) і скіла (D3)
- **AC31** (ubiquitous, US2) Редактор агента повинен (shall) мати вкладку «Context» між «Skills» і «Evals» (D2), яка відкривається через `?tab=context`. `[unit]` `[e2e]`
- **AC78** (ubiquitous, US2) Вкладка Context повинна (shall) показувати в заголовку повне ім'я активного репо: «Project context · {owner/name}» в агента і «Project context to use · {owner/name}» у скіла. `[unit]`
- **AC32** (ubiquitous, US2) Вкладка Context агента або скіла повинна (shall) показувати спершу власні прикріплення в збереженому порядку (з відповіді `ContextAttachments`), потім решту документів репо за `path`. У кожному рядку — grip, checkbox, ім'я файлу, тека, тег категорії, кількість токенів документа «{n} tok» і кнопка Preview. `[unit]`
- **AC33** (event, US2) КОЛИ користувач позначає checkbox неприкріпленого документа у вкладці Context, система повинна (shall) зберегти прикріплення для активного репо без окремої кнопки Save, додавши документ у кінець списку прикріплених. `[unit]` `[it]`
- **AC84** (event, US2) КОЛИ користувач знімає checkbox прикріпленого документа у вкладці Context, система повинна (shall) прибрати його з прикріплень для активного репо без окремої кнопки Save, зберігши порядок решти. `[unit]` `[it]`
- **AC34** (event, US2) КОЛИ користувач перетягує прикріплений рядок на нову позицію серед прикріплених, система повинна (shall) зберегти новий порядок без окремої кнопки Save. `[unit]` `[it]`
- **AC35** (event, US2) КОЛИ фокус на grip прикріпленого рядка й користувач натискає ArrowUp або ArrowDown, система повинна (shall) перемістити документ на одну позицію вгору або вниз серед прикріплених і зберегти порядок. На крайній позиції нічого не відбувається. `[unit]`
- **AC80** (ubiquitous, US2) Grip неприкріплених рядків повинен (shall) бути видимим, але disabled: такий рядок не перетягується й не реагує на ArrowUp/ArrowDown. Порядок задається лише серед прикріплених. `[unit]`
- **AC36** (state, US2) ПОКИ поле «Filter documents…» непорожнє, UI повинен (shall) показувати лише рядки, чий `path` містить введений текст без урахування регістру, а grip-и повинні бути disabled. Якщо збігів немає, UI показує «No documents match "{q}"». `[unit]`
- **AC37** (ubiquitous, US2) Вкладка Context агента повинна (shall) показувати бейдж «{attached} of {total} attached» (D2), де attached — кількість власних прикріплень агента для репо з будь-яким `status` (успадковані не враховуються), а total — кількість документів репо у відповіді списку. attached може включати шляхи за межею 500, тож «3 of 500 attached» — коректний стан. Вкладка скіла показує бейдж «{attached} attached» (D3). `[unit]`
- **AC38** (unwanted, US2) ЯКЩО збереження прикріплень з вкладки Context не вдалося, ТОДІ UI повинен (shall) повернути рядки в стан до зміни й показати toast «Couldn't save context: {message}». `[unit]`
- **AC39** (ubiquitous, US2) Вкладка Context **агента** повинна (shall) показувати внизу «≈ {N} tokens / 8,000», де N — сума `tokens` усіх власних і успадкованих документів агента зі `status: "ok"` до застосування бюджету з AC60, і текст «Injected as an untrusted block (## Project context) into every run.». Вкладка скіла цього футера не показує. `[unit]`
- **AC40** (state, US2) ПОКИ N з AC39 перевищує 8 000, вкладка Context агента повинна (shall) показувати поруч із сумою попередження кольором warning «Over the 8,000-token budget — documents past the limit are skipped at run time.». `[unit]`
- **AC77** (optional, US2) ДЕ стратегія агента `map-reduce` або `auto`, вкладка Context агента повинна (shall) показувати під сумою підказку «With map-reduce this block is sent with every per-file call — its cost multiplies by the number of changed files.». `[unit]`
- **AC41** (ubiquitous, US2) Вкладка Context агента повинна (shall) показувати після власних прикріплених рядків документи з `inherited` (успадковані від прикріплених і увімкнених скілів агента, яких агент не прикріпив сам) у порядку злиття з AC57. Кожен такий `path` показується один раз, read-only рядком з позначкою «via {skill name}», без checkbox і grip, але з кнопкою Preview для `status: "ok"`. Серед решти документів репо цей `path` не повторюється. `[unit]` `[it]`
- **AC42** (unwanted, US2) ЯКЩО власне прикріплення має `status: "missing"`, ТОДІ вкладка Context повинна (shall) показати його рядком із позначкою «missing», кнопкою «Detach» і без токенів. Натискання Detach прибирає прикріплення й зберігає список. `[unit]`
- **AC89** (unwanted, US2) ЯКЩО власне прикріплення має `status: "too_large"`, ТОДІ вкладка Context повинна (shall) показати його рядком із позначкою «too large (> 1 MB)», кнопкою «Detach» і без токенів, а N з AC39 його не враховує. `[unit]`
- **AC90** (ubiquitous, US2) Вкладка Context повинна (shall) показувати власні прикріплення зі `status: "ok"` зі звичайним рядком і токенами навіть тоді, коли цього `path` немає серед перших 500 документів списку (`truncated: true`). `[unit]` `[it]`
- **AC43** (event, US2) КОЛИ користувач відкриває іншого агента чи скіл або відкриває вкладку Context після зміни активного репо, вкладка повинна (shall) показати документи й прикріплення саме цієї пари (агент/скіл, репо) і ніколи не зберігати рядки попередньої пари. (Перемикання репо зі сторінок `/agents/:id` і `/skills/:id` переводить на `/repos/<new>/pulls` — наявна поведінка.) `[unit]`
- **AC44** (unwanted, US2) ЯКЩО у вкладці Context API списку відповідає `repo_not_cloned`, ТОДІ вкладка повинна (shall) показати «Repository isn't cloned yet — sync it to see its documents.». `[unit]` `[e2e]`
- **AC85** (unwanted, US2) ЯКЩО в клонованому репо немає жодного документа, ТОДІ вкладка Context повинна (shall) показати замість списку неприкріплених «No Markdown documents found». `[unit]`
- **AC86** (unwanted, US2) ЯКЩО у воркспейсі немає активного репо, ТОДІ вкладка Context повинна (shall) показати «Add a repository to attach its documents.». `[unit]`
- **AC87** (unwanted, US2) ЯКЩО завантаження списку або прикріплень у вкладці Context завершилося помилкою (крім `repo_not_cloned`), ТОДІ вкладка повинна (shall) показати «Couldn't load documents» з кнопкою Retry. `[unit]`
- **AC88** (state, US2) ПОКИ список документів або прикріплення вкладки Context завантажуються, вкладка повинна (shall) показувати скелетони рядків. `[unit]`
- **AC45** (event, US2) КОЛИ користувач натискає Preview у рядку вкладки Context, UI повинен (shall) відкрити шухляду прев'ю з AC48 для цього документа (REC6). `[unit]`
- **AC46** (ubiquitous, US3) Редактор скіла повинен (shall) мати вкладку «Context» між «Config» і «Preview» (D3), відкривану через `?tab=context`, з підказкою «Any agent using this skill inherits these documents.». `[unit]`

- **AC49** (unwanted, US2) ЯКЩО вміст для шухляди прев'ю не завантажився, ТОДІ шухляда повинна (shall) показати «Couldn't load document» з кнопкою Retry. `[unit]`

### Прикріплення (API)
- **AC50** (event, US2) КОЛИ клієнт викликає `PUT /agents/:id/context?repo_id=<r>` або `PUT /skills/:id/context?repo_id=<r>` з тілом `{ paths }`, API повинен (shall) замінити прикріплення цієї пари (агент/скіл, репо) на переданий список у переданому порядку й повернути збережений стан у формі `ContextAttachments`. `[it]`
- **AC51** (event, US2) КОЛИ клієнт викликає `GET /agents/:id/context?repo_id=<r>`, API повинен (shall) повернути `attached` — прикріплення агента для репо в збереженому порядку, кожне з `status` (`ok` | `too_large` | `missing`, за станом файлу в робочому дереві клону незалежно від ліміту 500) і `tokens` (число лише для `ok`), — та `inherited` — документи увімкнених скілів, увімкнено прикріплених до агента, у порядку AC57, без тих, що вже є в `attached`, з `skill_id`, `skill_name`, `status` і `tokens`. Шлях, чий realpath лежить за межами клону або який проходить через symlink на теку, отримує `status: "missing"` і не читається (правила AC75). `[it]`
- **AC91** (unwanted, US2) ЯКЩО репо з `repo_id` не має клону або тека клону відсутня чи не є git-репозиторієм, ТОДІ API повинен (shall) відповісти 409 `repo_not_cloned` на `GET /agents/:id/context` і `GET /skills/:id/context`, як в AC6, а вкладка Context показує стан з AC44. `[unit]`
- **AC52** (unwanted, US2) ЯКЩО `paths` у PUT містить шлях, що порушує правила формату з AC9, повтор шляху або понад 50 елементів, ТОДІ API повинен (shall) відповісти 422 і не змінювати збережені прикріплення. `[unit]`
- **AC53** (unwanted, US2) ЯКЩО агента, скіла або репо з `repo_id` не існує у воркспейсі, ТОДІ API повинен (shall) відповісти 404 на `GET`/`PUT` прикріплень. `[unit]`
- **AC54** (ubiquitous, system) Система повинна (shall) видаляти прикріплення агента, скіла або репо разом із видаленням цього агента, скіла або репо. `[it]`
- **AC55** (ubiquitous, US2) Система не повинна (shall not) змінювати `version` агента чи скіла й не повинна створювати записи в `agent_versions` / `skill_versions` під час прикріплення, відкріплення чи зміни порядку. `[it]`
- **AC56** (event, US4) КОЛИ клієнт викликає `GET /repos/:id/context/usage?path=<p>`, API повинен (shall) повернути агентів і скіли воркспейсу (`id`, `name`), які прикріпили `p` для цього репо. `[it]`

### Запуск агента
- **AC57** (event, US5) КОЛИ стартує запуск агента на PR у репо R, система повинна (shall) скласти список документів так: спершу прикріплення агента для R у їхньому порядку, потім для кожного скіла, прикріпленого до агента й увімкненого (і зв'язок, і сам скіл), у порядку скілів агента — прикріплення скіла для R у його порядку. Повтори одного `path` прибираються, перший запис виграє. `[unit]`
- **AC58** (event, US5) КОЛИ список з AC57 складено, система повинна (shall) читати вміст кожного документа з tip гілки `origin/<base>` PR (базова гілка) у локальному клоні, а не з `head_sha` PR. `[unit]`
- **AC59** (event, US5) КОЛИ є хоча б один прочитаний документ, що вміщається в бюджет, система повинна (shall) передати їхні тексти в порядку AC57 у секцію `## Project context` user-повідомлення, кожен в окремому `<untrusted>`-блоці. `[unit]`
- **AC60** (unwanted, US5) ЯКЩО cl100k-кількість токенів блоку Project context (повний текст, як у `prompt_assembly.specs`, разом із роздільниками) з наступним документом (у порядку AC57) перевищить 8 000, ТОДІ система повинна (shall) пропустити цей документ цілком, продовжити з наступними й записати в Live Log рядок `Project context: skipped <path> (budget)`. `[unit]`
- **AC61** (unwanted, US5) ЯКЩО документа немає в `origin/<base>`, він більший за 1 048 576 байт або не читається, ТОДІ система повинна (shall) пропустити його, записати в Live Log рядок `Project context: skipped <path> (missing)` і продовжити запуск. `[unit]`
- **AC62** (ubiquitous, US5) reviewer-core повинен (shall) приймати документи як пари `{ path, content }` і позначати untrusted-блок кожного як `source="spec:<path>"`, замінюючи в `path` символи `"`, `<`, `>` на `_` (REC5). `[unit]`
- **AC63** (unwanted, US5) ЯКЩО репо PR не має клону або тека клону відсутня, ТОДІ система повинна (shall) запустити рев'ю без секції `## Project context` і записати в Live Log `Project context: repo not cloned — skipped`. `[unit]`
- **AC79** (unwanted, US5) ЯКЩО ref `origin/<base>` відсутній у локальному клоні (наприклад, shallow single-branch клон без базової гілки), ТОДІ система повинна (shall) запустити рев'ю без секції `## Project context` і записати в Live Log рівно один рядок `Project context: base branch <base> not fetched — skipped`, не робивши fetch. Відсутність ref визначається окремою перевіркою наявності ref, а не результатом читання файлу, тож відсутній ref не плутається з відсутнім документом (AC61). `[unit]`
- **AC64** (state, US5) ПОКИ для агента та його увімкнених скілів у репо PR немає жодного прикріплення, система повинна (shall) збирати промпт без секції `## Project context` (так само, як до цієї фічі) і записувати в Live Log `Project context: none attached`. `[unit]`
- **AC65** (event, US5) КОЛИ блок Project context зібрано з ≥ 1 документа, система повинна (shall) записати в Live Log рядок `Project context: {n} doc(s), +{T} tokens — {path1}, {path2}, …`. `[unit]`
- **AC82** (unwanted, US5) ЯКЩО прикріплення є, але всі документи пропущено (AC60, AC61), ТОДІ система повинна (shall) запустити рев'ю без секції `## Project context` і записати в Live Log рядок `Project context: no documents injected (all skipped)` замість рядка з AC65. `[unit]`
- **AC76** (ubiquitous, US5) Під стратегією map-reduce система повинна (shall) включати той самий блок `## Project context` у кожен per-file map-виклик. Бюджет 8 000 токенів з AC60 діє на кожен LLM-виклик, тож вартість блоку множиться на кількість map-викликів. `[unit]`
- **AC66** (ubiquitous, system) Система повинна (shall) додавати тексти документів лише в user-повідомлення всередині `<untrusted>`-блоків і не повинна змінювати `INJECTION_GUARD` чи grounding gate. `[unit]`
- **AC67** (ubiquitous, US5) Система повинна (shall) використовувати набір прикріплень, прочитаний на старті запуску. Зміни прикріплень під час запуску діють лише на наступні запуски. `[unit]`
- **AC68** (ubiquitous, US6) Система повинна (shall) записувати в трасу завершеного запуску `specs_read` — шляхи фактично вставлених документів у порядку вставлення, `prompt_assembly.specs` — повний текст блоку, і `block_tokens.specs` — його кількість токенів. Для запуску без вставлених документів `specs_read` — `[]`, а `prompt_assembly.specs` — `null`. `[unit]` `[it]`
- **AC69** (ubiquitous, US5) Система повинна (shall) застосовувати AC57–AC68, AC76, AC79 і AC82 до кожного запуску рев'ю незалежно від того, хто його ініціював: UI («Run Review», Multi-Agent Review) чи MCP-тул `run_agent_on_pr`. `[it]`

### Траса запуску (D4)
- **AC70** (ubiquitous, US6) Шухляда запуску повинна (shall) показувати в Configuration рядок «Specs read» зі шляхами з `specs_read` через пробіл у збереженому порядку (D4), або «none», якщо список порожній. `[unit]`
- **AC71** (ubiquitous, US6) Розділ Prompt assembly повинен (shall) показувати рядок «Project context — attached specs (untrusted)» (D4) для траси, де `prompt_assembly.specs` непорожній, з кількістю токенів з `block_tokens.specs`. `[unit]`
- **AC72** (event, US6) КОЛИ користувач натискає «expand» у рядку «Project context — attached specs (untrusted)», UI повинен (shall) показати повний текст `prompt_assembly.specs` без обрізання. `[unit]`
- **AC73** (event, US6) КОЛИ користувач натискає copy у цьому рядку, UI повинен (shall) скопіювати в буфер обміну повний текст `prompt_assembly.specs`. Помилка буфера — наявна поведінка блоків Prompt assembly. `[unit]`
- **AC74** (unwanted, US6) ЯКЩО `prompt_assembly.specs` траси `null` або відсутній (запуск без документів або траса, записана до цієї фічі), ТОДІ UI не повинен (shall not) показувати рядок Project context у Prompt assembly й не повинен падати. `[unit]`

## Edge cases
- **EC1** Документ більший за 1 MB → показано як «too large», не прикріплюється, при запуску пропускається (AC4, AC20, AC61).
- **EC2** У репо понад 500 Markdown-файлів → перші 500 за шляхом плюс повідомлення (AC5, AC21).
- **EC3** Прикріплений документ видалено або перейменовано в репо → рядок «missing» з Detach у вкладці; під час запуску пропускається з рядком у Live Log (AC42, AC61).
- **EC4** Документ є в робочому дереві клону (дефолтна гілка), але його немає в базовій гілці PR → під час запуску пропускається як missing (AC58, AC61).
- **EC5** Сума прикріплених перевищує 8 000 токенів → попередження у вкладці; під час запуску документи, що не вміщаються, пропускаються, а менші наступні ще можуть увійти (AC40, AC60).
- **EC6** Один документ прикріплено і до агента, і до його скіла → вставляється один раз, на позиції прикріплення агента (AC57, AC41).
- **EC7** Скіл із прикріпленнями вимкнено глобально або його зв'язок з агентом вимкнено → його документи не потрапляють у промпт і не показуються як успадковані (AC57, AC41).
- **EC8** Репо не клоновано (зокрема seed-репо) → порожній стан на сторінці та у вкладках; запуск без Project context (AC18, AC44, AC63).
- **EC9** У воркспейсі немає репо → порожні стани з посиланням на додавання репо (AC19, AC86).
- **EC10** Прикріплення змінено під час запуску → запуск використовує набір зі свого старту (AC67).
- **EC11** Дві вкладки браузера одночасно зберігають прикріплення одного агента → виграє останній PUT, бо він замінює весь список (AC50).
- **EC12** Шлях з `..`, абсолютний шлях або symlink за межі клону в запиті → 422, файл не читається (AC9, AC52).
- **EC13** Markdown містить сирий HTML або посилання `javascript:` → не виконується й не стає активним посиланням (AC30).
- **EC14** Шлях документа містить `"`, `<` або `>` → у мітці untrusted-блоку ці символи замінено на `_` (AC62).
- **EC15** Агента, скіл або репо видалено → його прикріплення видаляються (AC54).
- **EC16** Траса, записана до цієї фічі → рядок Project context не показується, шухляда працює (AC74).
- **EC17** Фільтр активний під час спроби змінити порядок → reorder вимкнено (AC36).
- **EC18** Сервер перезапускається посеред запуску → наявна поведінка (reap `running`-рядків на boot); прикріплення лежать у БД і не губляться (NFR6).
- **EC19** У клоні є symlink на теку (зокрема циклічний) або symlink на файл поза клоном → тека не обходиться, файл не потрапляє в список (AC75). Прикріплений шлях, що проходить через такий symlink або веде за межі клону, у відповіді прикріплень отримує `status: "missing"` і не читається (AC51).
- **EC26** Агент відкрито у вкладці Context для репо, чий клон зник → 409 `repo_not_cloned` на прикріпленнях, порожній стан «не клоновано» (AC91, AC44).
- **EC20** Прикріплений документ став більшим за 1 MB або опинився за межею 500 у списку → рядок «too large» з Detach і без токенів, або звичайний рядок з токенами відповідно (AC89, AC90).
- **EC21** `clone_path` записано, але теки немає на диску або вона не є git-репо → 409 `repo_not_cloned` і порожній стан, а не 500; запуск без Project context (AC6, AC18, AC63).
- **EC22** Базової гілки PR немає в клоні (shallow single-branch) → один рядок у Live Log, запуск без Project context, без fetch (AC79).
- **EC23** Агент зі стратегією map-reduce на PR з 10 файлами → блок до 8 000 токенів іде в кожен із 10 map-викликів; вкладка попереджає про множення (AC76, AC77).
- **EC24** Усі прикріплені документи пропущено (budget або missing) → без секції й з одним підсумковим рядком у Live Log (AC82).
- **EC25** Усі документи репо більші за 1 MB або `?doc=` вказує на такий документ → вибрано цей документ, прев'ю показує повідомлення замість вмісту (AC14, AC81).

## Non-functional requirements
- **NFR1** Латентність API: `GET /repos/:id/context` для репо з 500 Markdown-файлами загальним розміром ≤ 5 MB відповідає за ≤ 2 000 мс (p95, 10 запитів на робочій машині розробника) — перевірка: `[manual]` розробник запускає запит 10 разів на фікстурному клоні й записує p95 у PR.
- **NFR2** Ліміт токенів: у будь-якому LLM-виклику (single-pass або кожен map-виклик) блок `## Project context` ≤ 8 000 токенів cl100k, і `block_tokens.specs` у трасі ніколи не перевищує 8 000 — перевірка: `[unit]` тест AC60 з документами приблизно по 5 000, 4 000 і 2 000 токенів (у блок входять 1-й і 3-й, `block_tokens.specs` ≤ 8 000).
- **NFR3** Латентність запуску: читання й токенізація до 50 прикріплених документів додають ≤ 500 мс до старту запуску (p95) — перевірка: `[manual]` розробник порівнює час між рядками Live Log «Skills: …» і «Project context: …» на 5 запусках.
- **NFR4** a11y (WCAG 2.2 AA): кожен checkbox має доступну назву — ім'я файлу; grip має `aria-label` «Reorder {file}» і працює з клавіатури (AC35); меню «Attach to…» і шухляда прев'ю керуються з клавіатури, Esc закриває — перевірка: `[unit]` запити за role/name у компонентних тестах і `[manual]` прохід лише клавіатурою перед мержем.
- **NFR5** i18n: усі нові рядки UI лежать у `client/messages/en/*.json` (`context.json`, `agents.json`, `skills.json`, `runs.json`), лічильники через ICU plural, у компонентах немає вбудованого тексту — перевірка: `[unit]` тести рендерять через next-intl-обгортку з `messages/en` і знаходять тексти з AC.
- **NFR6** Стійкість: прикріплення зберігаються лише в Postgres; після перезапуску сервера `GET` прикріплень повертає той самий порядок — перевірка: `[it]` PUT → новий інстанс app на тій самій БД → GET.
- **NFR7** Спостережуваність: у Live Log кожного запуску є рівно один рядок на кожен пропущений документ (AC60, AC61) і рівно один підсумковий рядок Project context, обраний за пріоритетом: немає прикріплень (AC64) → репо не клоновано (AC63) → немає ref базової гілки (AC79) → зібрано (AC65) або все пропущено (AC82). Перший застосовний випадок виграє, решта не логуються — перевірка: `[unit]` тест `log` траси для кожного з п'яти випадків.

## Untrusted inputs
- Вміст документа → prompt → окремий `<untrusted source="spec:<path>">`-блок у user-повідомленні, `INJECTION_GUARD` без змін, grounding без змін; документи не потрапляють у system-повідомлення (AC59, AC62, AC66). Читається з базової гілки, тож автор PR не може в цьому ж PR переписати документ, проти якого його перевіряють (AC58). Обсяг обмежено 1 MB на файл і 8 000 токенів на виклик (OWASP LLM10; AC4, AC60, AC76).
- Вміст документа → UI → Markdown без сирого HTML і без `javascript:`-посилань (AC30).
- `path` від клієнта → FS → без абсолютних шляхів, `..`, symlink-втечі, лише `.md`/`.mdx` поза виключеними теками; інакше 422 (AC9, AC52).
- Файлова структура клону → FS-сканування → symlink-теки не обходяться, symlink-файли поза клоном відкидаються (AC75).
- Шлях файлу (ім'я в репо) → prompt-мітка → символи `"`, `<`, `>` замінено (AC62); → UI → рендериться як текст.
- Скіли лишаються trusted-інструкціями, але документи, прикріплені до скіла, — untrusted, як і документи агента (AC57, AC59).

## Assumptions
- Список документів (сторінка, вкладки, `tokens`, `status` прикріплень) береться з робочого дерева клону (дефолтна гілка станом на останній sync). Під час запуску документи читаються з `origin/<base>`, тож розбіжність між ними трактується як missing (EC4).
- Відома межа захисту: базову гілку обирає автор PR. У stacked-PR (база — інша feature-гілка того ж автора) автор може змінити документи в базовій гілці. Окремого AC для цього немає.
- `tokens` у вкладці — оцінка («≈»): сума per-doc токенів може відрізнятися від `block_tokens.specs` траси на кілька токенів через роздільники між блоками. Бюджет запуску рахується по повному блоку (AC60).
- PUT прикріплень перевіряє лише формат шляху, а не наявність файлу в клоні, щоб reorder працював і з рядками «missing».
- Ліміт 50 прикріплень на пару (агент/скіл, репо) і межа списку 500 документів — рішення spec-creator.
- Точка входу на сторінку — пункт сайдбару «Project Context» у групі WORKSPACE, бо він намальований на всіх D1–D4. REC7 відхилено, тож перемикання репо зі сторінки зберігає наявну поведінку (перехід до списку PR нового репо), як і з `/agents/:id` та `/skills/:id`.
- Підзаголовок `.devdigest/specs/` з D1 замінено кількістю документів (AC13), бо пошук охоплює весь репо.
- Заголовок `## Project specifications` у блоці «SERIALIZES AS» на D3 замінено на `## Project context` — реальну назву секції промпту (`reviewer-core/src/prompt.ts:131`) (AC47).
- Підпис D1 «Used by 3 agents» розширено до «Used by {a} agents · {s} skills» з ICU plural, бо прикріплювати можна й до скілів (AC24).
- Футер D2 «≈ 317 tokens» розширено до «≈ N tokens / 8,000», щоб було видно бюджет запуску (AC39).
- До заголовків вкладок D2/D3 додано назву активного репо (AC78), бо прикріплення прив'язані до репо (рішення користувача в раунді 2).
- Renderer `Markdown` з `@devdigest/ui` побудований на `react-markdown` без `rehype-raw`. Вважається (не досліджено researcher-ом), що він за замовчуванням не рендерить сирий HTML і нейтралізує `javascript:`-URL. AC30 перевіряє це тестом.
- Клавіатурна альтернатива перетягуванню (AC35) відповідає WCAG 2.2 SC 2.5.7 Dragging Movements — відоме з загальних знань, researcher-ом не перевірено.
- Підпис рядка траси «Project context (dynamic)» замінюється на «Project context — attached specs (untrusted)» з D4.
- e2e-перевірки (AC18, AC31, AC44) виконуються на CI або на macOS ≥ 13: локальний хост на macOS 12 не запускає Chrome від agent-browser (`e2e/INSIGHTS.md`).
